# Triage

Move issues on the project issue tracker through a small state machine of triage roles.

If this repo treats external pull requests as a request surface — see the issue-tracker config — triage covers them too. **A PR is an issue with attached code**: same roles, same states, same machine, with a few differences marked "for a PR" below. Resolve a bare `#42` to an issue or a PR according to the tracker config.

Every comment or issue you post to the issue tracker during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — how to write durable agent briefs
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — how the `.out-of-scope/` knowledge base works

## Roles

Two **category** roles:

- `bug` — something is broken
- `enhancement` — a new feature or an improvement

Five **state** roles:

- `needs-triage` — the maintainer needs to evaluate it
- `needs-info` — waiting on the reporter for more information
- `ready-for-agent` — fully specified, ready for an AFK agent
- `ready-for-human` — needs a human to implement it
- `wontfix` — will not be actioned

For a PR, the same states read against the attached code. `ready-for-agent` means a brief is attached and an agent should take the next step on the diff. `ready-for-human` means a human can merge it.

Every triaged issue carries exactly one category role and one state role. If state roles conflict, flag it and ask the maintainer before you do anything else.

These are canonical role names. The label strings the issue tracker actually uses may differ. You should already have the mapping. Run `/setup-builder-tools` if you do not.

State transitions: an unlabeled issue normally goes to `needs-triage` first. From there it moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` once the reporter replies. The maintainer can override at any time. Flag any transition that looks unusual and ask before you proceed.

## Invocation

The maintainer invokes `/triage` and describes what they want in natural language. Interpret the request and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Query the issue tracker and present three buckets, oldest first:

1. **Unlabeled** — never triaged.
2. **`needs-triage`** — evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes** — needs re-evaluation.

When PRs are in scope, include external PRs in these buckets and tag each line `[PR]` or `[issue]`. Discovery surfaces only *external* PRs — the tracker config defines who counts as external — because a collaborator's in-flight PR is not triage work. This filter applies to discovery only. Always triage a PR the maintainer names explicitly, whoever wrote it.

Show counts and a one-line summary per item. Let the maintainer pick.

## Triage a specific issue or PR

1. **Gather context.** Read the full issue or PR: body, comments, labels, author, dates, and for a PR the diff too. Read any prior triage notes so you do not re-ask questions that are already resolved. Explore the codebase using the project's domain glossary, and respect the ADRs in the area. Then run two checks against the codebase. (a) **Redundancy** — search for an existing implementation of the requested behavior by domain concept, not only by the request's wording, and report where you looked. If you find one, this is an already-implemented `wontfix` (step 5). (b) **Prior rejection** — read `.out-of-scope/*.md` and surface anything that resembles this request.

2. **Recommend.** Tell the maintainer your category and state recommendation, with your reasoning, plus a short codebase summary relevant to the request — including whether the feature already exists. Wait for direction.

3. **Verify the claim.** Before any grilling, check that the claim holds up. For a bug, reproduce it from the reporter's steps. For a PR, confirm the diff does what it claims: check it out, and run the relevant tests or commands. Report what happened — confirmed (with the code path), failed, or not enough detail, which is a strong `needs-info` signal. A confirmed verification makes a much stronger agent brief.

4. **Grill (if needed).** If the request needs fleshing out, run the `/grilling` and `/domain-modeling` skills together. Grill it into shape one round of questions at a time, sharpening domain terms and updating `CONTEXT.md` and the ADRs inline as decisions land.

5. **Apply the outcome:**
   - `ready-for-agent` — post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human` — same structure as an agent brief, but say why you cannot delegate it: judgment calls, external access, design decisions, manual testing.
   - `needs-info` — post triage notes (template below).
   - `wontfix` — close it, with the comment depending on *why*:
     - **Already implemented** — the change already exists in the codebase. Point to where it lives. Do **not** write to `.out-of-scope/`. That knowledge base is for *rejected* requests, not built ones.
     - **Rejected (bug)** — a polite explanation, then close.
     - **Rejected (enhancement)** — write to `.out-of-scope/`, link to it from a comment, then close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage` — apply the role. Add a comment if there is partial progress.

## Quick state override

If the maintainer says "move #42 to ready-for-agent", trust them and apply the role directly. Confirm what you are about to do — role changes, comment, close — then act. Skip the grilling. If you are moving to `ready-for-agent` without a grilling session, ask whether they want an agent brief written.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything you resolved during grilling under "established so far", so the work is not lost. Make the questions specific and actionable, not "please provide more info".

## Resuming a previous session

If prior triage notes exist on the issue or PR, read them, check whether the reporter has answered any outstanding questions, and present an updated picture before you continue. Do not re-ask questions that are already resolved.
